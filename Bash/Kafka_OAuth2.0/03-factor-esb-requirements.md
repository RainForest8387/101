# Требования к «Фактор ЕСБ» как OAuth 2.0-провайдеру для Kafka

Публичной документации по «Фактор ЕСБ» найти не удалось, поэтому документ построен от обратного: вот что Kafka **обязана** получить от провайдера, чтобы SASL/OAUTHBEARER заработал. Список можно отправлять вендору или владельцу ЕСБ как есть.

## Блокирующие требования

Без любого из этих пунктов схема не заработает вообще — это первое, что нужно подтвердить.

| # | Требование | Зачем | Ответ ЕСБ |
|---|---|---|---|
| 1 | Grant type `client_credentials` (RFC 6749 §4.4) | Kafka-клиенты — сервисы, интерактивного пользователя нет | |
| 2 | Access token в формате **JWT** (не opaque) | брокер валидирует токен локально; introspection Kafka не поддерживает | |
| 3 | Подпись **асимметричная**: RS256 / RS384 / RS512 / ES256 / PS256 | брокер знает только публичный ключ; HS256 не годится | |
| 4 | Публичный **JWKS endpoint** (RFC 7517), доступный брокеру по сети | загрузка и кэш ключей проверки | |
| 5 | Заголовок JWT содержит `kid` | выбор нужного ключа из JWKS при ротации | |
| 6 | Claims `iss`, `exp` | обязательная проверка на брокере | |
| 7 | Claim с идентификатором сервиса (`sub`, либо `client_id`) | из него строится принципал `User:<...>` для ACL | |
| 8 | HTTPS на token и JWKS endpoint, CA известен | канал получения токена | |

## Важные, но обходимые

| # | Требование | Комментарий |
|---|---|---|
| 9 | Claim `aud` со значением, специфичным для Kafka (напр. `kafka`) | иначе токен, выданный для другой системы, подойдёт и к Kafka. Если ЕСБ не умеет — не задавать `expected.audience`, но это ослабление, и его надо зафиксировать в модели угроз |
| 10 | Настраиваемый TTL токена, 5–60 мин | слишком короткий — постоянные переподключения; слишком длинный — окно компрометации |
| 11 | Claim `scope` | сейчас Kafka не авторизует по scope, но пригодится при кастомном authorizer |
| 12 | Claim `jti` | сквозная корреляция журналов Kafka и ЕСБ при расследовании |
| 13 | Grant type `urn:ietf:params:oauth:grant-type:jwt-bearer` (KIP-1139) | позволяет уйти от хранения `client_secret` в конфигах — сильный плюс для ЗОКИИ |
| 14 | Discovery `/.well-known/openid-configuration` | Kafka не требует, но упрощает настройку и диагностику |
| 15 | Ротация ключей подписи без простоя (старый и новый ключ в JWKS одновременно) | иначе ротация = недоступность аутентификации |
| 16 | Отдельные service accounts под каждый сервис | принципал = аккаунт, а значит гранулярность ACL = гранулярность аккаунтов в ЕСБ |

## Вопросы, которые стоит задать вендору

1. Какой именно формат access token выдаёт ЕСБ — JWT или opaque? Если есть оба режима, как включить JWT?
2. Полный список claim'ов в токене для `client_credentials` — с примером реального токена (можно с затёртыми значениями).
3. Точные URL: token endpoint, JWKS URI, discovery. Значение `iss` — посимвольно, с завершающим слэшем или без.
4. Алгоритм подписи и наличие `kid`. Периодичность и процедура ротации ключей.
5. Как задаётся `aud`? Можно ли выдать токен с `aud=kafka` конкретному клиенту?
6. Диапазон настройки TTL. Что происходит при массовом одновременном обновлении токенов — есть ли rate limit на token endpoint?
7. Поддерживается ли `client_secret_basic`, `client_secret_post`, `private_key_jwt`, `jwt-bearer`?
8. Какой CA подписывает сертификат ЕСБ и как получить его цепочку для truststore брокеров?
9. Отзыв доступа: как быстро блокировка service account в ЕСБ приводит к отказу в аутентификации? (Ответ обычно — «через TTL уже выданного токена», это надо зафиксировать.)
10. Есть ли у ЕСБ ГОСТ TLS-only режим? Если да — см. раздел о криптографии в `01-alt-linux-packages.md`, OpenJDK его не поддерживает.
11. Резервирование ЕСБ: SLA доступности, есть ли второй ЦОД. Недоступность ЕСБ = невозможность подключения новых клиентов Kafka.

## Как проверить ответы, не дожидаясь стенда

Скрипт `stand/test-oauth.sh` шагами 1–5 проверяет ровно эти требования по реальному endpoint'у ЕСБ, без Kafka:

```bash
ISSUER=https://esb.example.ru \
TOKEN_URL=https://esb.example.ru/oauth2/token \
JWKS_URL=https://esb.example.ru/oauth2/jwks \
CLIENT_ID=kafka-test CLIENT_SECRET=... \
CACERT=/etc/pki/esb-ca.crt \
./test-oauth.sh
```

Шаг 4 печатает разбор claim'ов и явно отмечает, каких обязательных полей не хватает; шаг 5 проверяет, что подпись токена сходится с ключом из JWKS. Этого достаточно, чтобы за 5 минут понять, взлетит схема или нет.

## Минимальный набор сервисных учёток на старт

| Учётка | Назначение | scope (предложение) | ACL |
|---|---|---|---|
| `kafka-broker` | inter-broker аутентификация | `kafka:broker` | super.user |
| `kafka-admin` | администрирование, CLI | `kafka:admin` | super.user |
| `kafka-ui` | подключение веб-интерфейса к кластеру | `kafka:admin` | Describe на весь кластер, Read по необходимости |
| `svc-<имя>` | по одной на каждый прикладной сервис | `kafka:read` / `kafka:write` | точечные ACL на конкретные топики и consumer-группы |
