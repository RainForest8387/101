##### Совокупность нескольких факторов

###### 0. Mirror Maker это Kafka Connect который выполняет более узкий круг задач, соотвественно все паттерны поведения, болячки и т.п у них одни и те же

###### 1.Параметр scheduled.rebalance.max.delay.ms 
отвечает за период после которого координатор считает воркер неработоспособным и начинает процесс передачи его задан на другие доступные воркеры (дефолтное значение 300000 мс = 5 минут)

Судя по логу

02:31:14 — воркер вернулся, generation 337:
           taskIds=[], delay=245902
02:35:20 — таймер истёк, generation 338:
           taskIds=[MirrorSourceConnector-0, MirrorSourceConnector-4], delay=0

delay=245902 — это остаток таймера в миллисекундах, 246 секунд из 300. Воркер вернулся уже через минуту, но получил пустое назначение (тот самый )

всё это время task-0 и task-4 не работали. Они не были назначены ни ноде 01, ни любой другой. Репликация партиций этих тасков не работала, пять минут простоя это цена настройки по умолчанию при каждом патчинге/остановке ноды.

###### 2. Таски вернулись на первую же ноду
Тут ирония в том что воркер на первой ноде успел вернуться "в строй" до истечения параметра указанного в п.1
Логика такая: 
когда таймер истекает прцесс идт по одну из двух путей
воркер вернулся -> таски отдаются ему обратно, распределение восстанавливается в исходный вид;
воркер не вернулся → таски раздаются оставшимся членам группы.
у нас воркер успел вернутся
судя по логам воркер вернулся в 02:31:14, 
к 02:35:20 был живым членом группы generation 338, и Kafka Connect Assignment (процесс который решает кому какие задачи передать) отдал ему ровно те же самые таски, которые за ним резервировал.
Начался паралельный старт двух тасков сразу (в нормальной ситуации один таск на один воркер распределяется, только в каких-то переходных состояниях несколько тасков попадают на один воркер, ну или если тасков больше чем воркеров из-за конфигурации) и вот здесь возник известный баг Kafka Connect (ConnectorStatusMetricsGroup recordTaskRemoved NullPointerException)
java.lang.NullPointerException
	at org.apache.kafka.connect.runtime.Worker$ConnectorStatusMetricsGroup.recordTaskRemoved(Worker.java:2334)
	at org.apache.kafka.connect.runtime.Worker.startTask(Worker.java:708)
Worker.startTask в блоке обработки ошибки вызывает recordTaskRemoved, чтобы убрать метрику таска. Внутри ConnectorStatusMetricsGroup идёт обращение к структуре, которой для этого коннектора ещё нет.

Проще говоря когда воркеру назначают один таск - все в пордяке, когда больше одного паралельно то бывает что происходит у него внутрення ошибка описанная выше, начинается гонка, какой-то из тасков успеет запустится а какой то нет, в нашем случае оба не успели

###### 3.FAILED — состояние таска, из которого Kafka Connect автоматически не выходит, только ручной перезапуск в явном виде
Ребаланс в Kafka Connect запускается по строго определённым событиям:

- воркер вступил в группу или покинул её;
- изменилась конфигурация (новая запись в config-топике);
- коннектор пересоздал конфиги тасков;
- явный вызов REST API.


Что делать чтобы не повторилась эта ситуация пока не будет официального исправления в новых версиях Kafka (у нас и Kakfka Connect и Mirror Maker часть дистрибутива Apache Kafka):
Не допускать параллельного старта двух тасков одного коннектора на одном воркере.
Для этого перезапускать воркеры строго по одному с полным ожиданием стабилизации, чтобы assignment менялся минимально. И не делать rolling restart с маленькими промежутками по вермени всех пяти, как утром 29-го.

Восстановление после падения — только через рестарт таска, воркер этого не сделает:
curl -X POST 'http://localhost:8083/connectors/MirrorSourceConnector/restart?includeTasks=true&onlyFailed=true'

Внести изменения:
1. Уменьшить период до 60 сек
scheduled.rebalance.max.delay.ms=60000
Компромисное значение, быстрее будет происходить ребаланс при реальном падении ноды, но больше лишних ребалансов при коротких плановых рестартах.
2. Чтобы работали вызовs REST API прописать в явном виде в connect-mirror-maker.properties значение listeners = http://0.0.0.0:8084
3. мониторинг FAILED-тасков
4. рестарт FAILED-тасков вместо рестарта воркера при восстановлении
На подумать:
перенос MM на отдельные ВМ, чтобы пачтинг не затрагивал одновременно и брокеры где хранится вся конфигурация ММ и сами воркеры ММ
